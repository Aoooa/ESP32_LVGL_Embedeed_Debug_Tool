# LVGL 文本滚动刷新性能优化报告

> 平台参考：ESP32-S3（240MHz 双核 + Octal PSRAM）+ SPI 接口 TFT LCD（240×320，80MHz）+ LVGL 9.4
> 场景：串口/日志数据持续到达，屏幕终端式滚动显示文本（10ms 一条数据流）

---

## 1. 背景与目标

在嵌入式 GUI 上实现"终端式"的持续文本滚动（串口日志、调试输出、数据流监视），
典型诉求：

- 数据到达及时显示（低延迟）
- 滚动流畅、无撕裂、无错位
- 支持触摸上下拖动查看历史

本文按 **显示链路逐环节分析瓶颈**，给出分层优化方案与实测数据。
方案与结论对 ESP32/STM32 + LVGL 8/9 + 各类 LCD 接口（SPI/8080/RGB）通用。

---

## 2. 显示链路与瓶颈分析

数据从产生到屏幕显示经过以下环节，每一环都可能成为瓶颈：

```
串口/数据源 → 应用读取任务 → 数据队列 → LVGL 任务(lv_timer_handler)
            → 渲染(draw) → flush(驱动/SPI DMA) → LCD
```

### 2.1 数据读取节奏（最容易忽略的瓶颈）

若应用用阻塞读取 + 长超时（如 100ms）轮询数据源，则**无论显示端多快，
帧率上限 = 读取频率**。10ms 一条的数据流配 100ms 读取，实测 FPS 恒为 10。

> 优化：读取超时降到数据间隔量级（10ms），并确认接收缓冲无溢出丢失。

### 2.2 LVGL 刷新周期（帧率硬上限）

`LV_DEF_REFR_PERIOD`（默认 33ms）直接决定渲染调度上限：

| 周期 | 帧率上限 |
|---|---|
| 33ms | 30 FPS |
| 15ms | 66 FPS |
| 10ms | 100 FPS |

官方基准与多数实践建议 10–15ms。**这是单点收益最大的配置**。

> 注意：部分组件/构建流程会覆盖该配置值，须在最终产物中确认生效
> （如 build/config 中核对宏值）。

### 2.3 label 文本总量（渲染开销 ∝ 文本量）

**实测结论：LVGL label 的渲染开销与"文本总量"成正比，与"可见区域"无关。**
同一 label 内文本越长，每次刷新（含折行重排与字形绘制）越慢：

- 8KB 全量文本：约 6 FPS（每帧 100ms+）
- 2KB 窗口文本：26 FPS（33ms 周期下的上限）

> 依据：lvgl/lvgl #640（textarea 16KB 卡死）、#5459（v9 在 ESP32 渲染慢 38%）。

### 2.4 失效区域与渲染/传输量

LVGL 按**失效区域**渲染，但：

- 全对象失效（`lv_obj_invalidate`）→ 整区域重绘 + 整区域 flush
- 局部失效（`lv_obj_invalidate_area`）→ 只重绘/传输局部
- **FULL 渲染模式**（全帧缓冲）→ 任何变化都整帧重绘

对 SPI 类接口，每帧传输量 = 失效区域像素 × 2B。全屏文本场景实测
**CPU 渲染占 27–44ms/帧，SPI flush 仅 2–6ms**（esp-bsp #806）——
文本场景的瓶颈在渲染，不在总线。

### 2.5 内存位置（PSRAM 的陷阱）

- **内部 SRAM 缓冲是 SPI/8080 面板的正确选择**（官方实测优于 PSRAM）
- PSRAM 源缓冲会触发 SPI 驱动在 ISR 中分配内部 DMA 中转缓冲，
  实测分配失败导致黑屏（IDF 5.5.3 无 PSRAM 直读 flag，esp-idf #18282；
  新版开启后在 WiFi 下有 underflow 风险，#18764）
- 内部 RAM 预算紧张时：优先压缩 LVGL 内存池、显示条带数量，
  将**任务栈**移到 PSRAM（`xTaskCreateWithCaps(MALLOC_CAP_SPIRAM)`）

### 2.6 触摸/事件（交互层瓶颈）

- `lv_obj_add_event_cb` 的 filter 参数是**单个事件码**，不支持位或！
  `PRESSED|PRESSING|RELEASED` = 11 = `LV_EVENT_SCROLL_THROW_BEGIN`
  （事件码在 lv_event.h 中为 1/2/9），导致回调收不到预期事件。
  应分别注册或使用 `LV_EVENT_ALL` 后自行过滤。
- 事件注册必须挂在**实际接收点击的对象**上（全尺寸子对象会遮挡父对象且事件不冒泡）。

## 3. 优化方案

### 3.1 配置层（零代码，先做）

| 项 | 建议 | 说明 |
|---|---|---|
| `LV_DEF_REFR_PERIOD` | 10–15ms | 帧率上限 |
| 双核渲染 | `LV_DRAW_SW_DRAW_UNIT_CNT=2` | 需 LV_USE_OS 启用 |
| `LV_OBJ_STYLE_CACHE` | 开 | 9.4 默认关，maintainer 点名 |
| 编译器优化 | -O2 | 渲染代码收益明显 |
| LVGL 关键代码 IRAM | 开 | 渲染路径避免 flash 缓存抖动 |
| wifi/lwip 缓冲 | PSRAM | 释放内部 RAM |
| 显示缓冲 | 内部 RAM 双缓冲，≥20% 屏高 | 官方实测缓冲曲线：<10% 严重劣化，>25% 无收益 |

### 3.2 渲染架构层（核心方案：canvas 位图窗口）

**方案**：放弃"长 label 持续增长"，改用 **canvas 位图 + 文本行历史**：

```
数据 → 逐字符解析（宽度累加折行）→ 环形行历史（文本）
     → 每帧从历史重建"可见窗口"位图（全量重绘 12 行）
     → 只失效 canvas（图像 blit，无文本重排开销）
```

要点：

1. **文本源唯一**（行历史数组），窗口内容由历史重建——
   彻底消除"批量缓冲索引错位""滚动后局部失效残留"等状态类 bug
2. **每帧全窗口重绘**（而非 memmove 增量）：memmove 会改变整个窗口的
   像素位置，仅失效底部条带会导致上方残留旧帧（实测"上方空白" bug）
3. 渲染量恒定（只画可见行），与历史总长无关
4. 触摸查看历史 = 从历史重建窗口（低频操作，全量重绘可接受）

**性能对比（10ms 数据流）**：

| 方案 | FPS |
|---|---|
| label 全量刷新（8KB，33ms 周期） | 10 |
| label 窗口裁剪（2KB，15ms） | 23–28 |
| canvas 窗口 + 10ms 周期 | 93（增量路径） |
| canvas 窗口 + 全量重绘（最终方案） | 34–45 |

> 最终方案选择"全量重绘"换取正确性与简单性；增量路径（93 FPS）可作为
> 后续优化方向，但必须处理"memmove 后全窗口失效"这一约束。

### 3.3 数据管道层

- 读取超时与数据节奏匹配（10ms）
- 数据解析与位图操作尽量在锁外（纯内存），锁内只做 LVGL API 调用
- 任务栈放 PSRAM，避免与显示缓冲争抢内部 RAM 导致任务创建失败

### 3.4 触摸交互层

- 事件回调挂到 canvas（实际点击对象），filter 用 `LV_EVENT_ALL`
- 拖动灵敏度：约半行高 = 1 行（7px/行），比 1:1 更跟手
- 语义：无触摸 → 跟随底部（数据到达即刷新）；触摸 → 暂停跟随，
  数据继续入历史、滚动条位置指示实时更新；滑回底部 → 自动恢复跟随

## 4. 实测数据汇总

测试条件：ESP32-S3 + ST7789(SPI 80MHz) + LVGL 9.4，10ms 一条数据流：

| 阶段 | FPS | 备注 |
|---|---|---|
| 原始（label + 100ms 读取 + 33ms 周期） | 10 | 读取节奏是主因 |
| label 窗口化 + 15ms 周期 | 23–28 | 33ms 周期上限 30 被周期限制 |
| canvas 增量 + 10ms 周期 | 93 | 渲染/失效最优 |
| canvas 全量重绘 + 10ms 周期 | 34–45 | 最终交付（正确性优先） |

## 6. 结论

1. **先测量，后优化**：帧率=读取节奏 ∩ 刷新周期 ∩ 渲染成本的最小值，
   逐一打点定位（FPS 统计 + 耗时日志）
2. **配置层收益最大**：刷新周期 10ms 是单点最高杠杆
3. **文本渲染架构决定上限**：label 文本总量是硬约束，
   canvas 位图窗口是文本滚动场景的正确形态
4. **正确性优先**：全量重绘换简单可靠；增量优化必须处理全窗口失效约束
5. **内存位置是硬约束**：显示缓冲必须内部 RAM，任务栈/大数据放 PSRAM
